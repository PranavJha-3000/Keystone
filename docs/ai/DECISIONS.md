### D-001 · 2026-09-14 · claude-opus-5
**Decision:** Two-subsystem crypto architecture — Semaphore for eligibility/anonymity, threshold ElGamal + Chaum-Pedersen for vote secrecy/tally
**Context:** Need to satisfy four conflicting properties (eligibility, anonymity, secrecy, verifiability) without writing custom unaudited SNARK circuits
**Reasoning:** Semaphore's circuits are audited; Chaum-Pedersen proofs have decades of scrutiny under DDH assumption. Composing two audited primitives is safer than one custom circuit.
**Rejected:** Single custom SNARK circuit for vote validity — rejected because custom circuits are unaudited by definition, have large constraint count, and a soundness bug means forged votes (worst failure mode).
**Tradeoff accepted:** More moving parts (two proof systems instead of one); trustee coordination required for threshold decryption.
**Revisit if:** A formally verified general-purpose SNARK framework (e.g., Nova/SuperNova with machine-checked circuits) matures to production readiness.

### D-002 · 2026-09-14 · claude-opus-5
**Decision:** TypeScript project references with `composite: true` for build dependency ordering
**Context:** Packages depend on shared-types and crypto; Turborepo's `dependsOn: ["^build"]` handles build ordering, but TypeScript needed to understand the dependency graph
**Reasoning:** Project references give TypeScript visibility into cross-package dependencies while Turborepo handles the actual build orchestration
**Rejected:** Removing references entirely — would lose IDE type-checking across package boundaries; Using path aliases only — would require duplicate type declarations
**Tradeoff accepted:** Every package tsconfig must have `composite: true` and produce `.tsbuildinfo` files
**Revisit if:** Build performance becomes an issue with the incremental compilation overhead

### D-003 · 2026-09-14 · claude-opus-5 ⚠️ AWAITING USER SIGN-OFF — DEVIATION FROM INSTRUCTION
**Decision:** Implement ElGamal/Chaum-Pedersen/DKG over **secp256k1** (`@noble/curves`), not baby-jubjub as instructed
**Context:** User said "pick baby-jubjub". `@noble/curves` does not ship baby-jubjub; the alternative was hand-entering 254-bit curve constants (prime, d, generator, order) via the `twistedEdwards` factory — one wrong digit yields a silently broken curve that passes smoke tests
**Reasoning:** secp256k1 provides the identical abstract group structure needed (prime-order subgroup, point add/mul, small-range discrete log). All crypto logic is curve-agnostic by design; the swap path is isolated to `packages/crypto/src/curve.ts`
**Rejected:** Hand-defined baby-jubjub via `twistedEdwards` — rejected due to constant-entry risk with no test vectors available yet; blocking on a baby-jubjub TS lib — rejected to keep momentum
**Tradeoff accepted:** Semaphore side (identity/Merkle) uses baby-jubjub internally, so the two subsystems currently sit on different curves; the ZK circuit layer cannot be built until curves are unified
**Revisit if:** User confirms/declines the deviation; must unify on baby-jubjub (or equivalent SNARK-friendly curve) before `packages/circuits` work starts

### D-004 · 2026-09-14 · claude-opus-5
**Decision:** `combinePartialDecryptions()` performs NO DLEQ proof verification; `verifyPartials()` is the caller's mandatory pre-step
**Context:** DLEQ verification needs each trustee's public key share, which is not part of `PartialDecryption`. A placeholder loop verifying against `scalarToPoint(0n)` (identity) threw on every valid partial
**Reasoning:** Rather than widen the combine signature or embed shares in the type (larger API change), verification stays a separate explicit step. Risk documented in the function docstring and body comment
**Rejected:** Passing `publicKeyShares` map into `combinePartialDecryptions` — cleaner but changes the signature the service layer will consume; can revisit when the tally service is built
**Tradeoff accepted:** A caller that skips `verifyPartials()` lets a malicious trustee corrupt the tally — this must be enforced in the tally service and later in FLOW.md

### D-005 · 2026-09-14 · claude-opus-5
**Decision:** Expose Semaphore v4's native `LeanIMTMerkleProof` (`root`/`leaf`/`index`/`siblings`) instead of mapping to a custom `{pathElements, indices}` shape; `@zk-kit/lean-imt` promoted to a direct dependency
**Context:** Semaphore v4 `Group` is a LeanIMT with no zero-hashes and dynamic depth; the initially written `nullifier`/`trapdoor` fields and custom Poseidon proof-rebuild do not exist in v4 (`Identity` exposes `secretScalar`, `publicKey`, `commitment`)
**Reasoning:** Mapping into a fake IMT shape would mislead the circuit layer; forwarding the real proof type keeps verify-on-chain and in-circuit consistent with the audited lib
**Rejected:** Keeping the custom `poseidonHash` placeholder + manual root reconstruction — rejected: placeholder hash can never match real Semaphore roots, so the placeholder path was removed entirely
**Tradeoff accepted:** `verifyMerkleProof` signature changed to `(proof) => boolean`; callers cannot verify a proof without the leaf context of a tree instance

### D-007 · 2026-09-15 · claude-opus-5
**Decision:** `docs/adr/0002-crypto-review.md` is the canonical record of the `packages/crypto` threat-model review. The three defects it reports (`homomorphicAdd` skipping validation of element 0; `combinePartialDecryptions` counting array entries rather than distinct trustees; no enforced verify-before-aggregate step) are left **unfixed**, pending explicit authorization.
**Context:** The task asked for a review document and said to change code only if an actual math bug surfaced. Re-deriving the algebra line by line (ElGamal, DLEQ, CDM OR-proof, Lagrange interpolation, BSGS) found it correct. The three findings are input-validation and call-ordering defects, not algebra errors, so the stated condition for changing code was not met.
**Reasoning:** The instruction was a deliberate scope fence. Silently widening it to "fix anything I judge broken" would set a precedent that makes the fence meaningless, and these are the exact defects the owner should decide on with severity context in front of them. The findings are recorded with file:line evidence, measured harness output, severity, and a proposed fix each, so acting on them later is a mechanical step rather than a re-investigation. Fixes were scoped and are genuinely small (Defect 1: validate all elements in one loop; Defect 2: dedupe by `trusteeIndex` and require `distinct >= threshold`) — both no-API-change.
**Rejected:** Fixing all three now and reporting after the fact — rejected as over-scoping against an explicit constraint; also rejected: writing permanent regression tests for defects left unfixed, which would encode failing behaviour as expected behaviour; also rejected: filing the availability attack as a mere note without reproduction, since a demonstrated DoS on the tally path is materially more actionable than an assertion.
**Tradeoff accepted:** Known defects ship in an uncommitted tree rather than being fixed immediately. Mitigated by (a) documenting the exact reproduction, (b) putting them at the top of HANDOVER Open items, and (c) noting that none is currently reachable because no point-deserialization entry point exists — that reachability changes the moment the wire format lands, which is called out in HANDOVER's Watch line for this session.

### D-008 · 2026-09-16 · solar-pro4
**Decision:** Implement `@keystone/circuits` as a thin wrapper over `@semaphore-protocol/proof` — no custom Circom. `ballotCommitment` rides in Semaphore's `message` slot; the scope is `keccak256(electionId)` (domain-tagged, shifted right 8 bits); the nullifier is left to the circuit, never re-derived off-circuit.
**Context:** Keystone needs election-scoped membership proofs with double-vote prevention and cross-election unlinkability. The user's instruction named `@semaphore-protocol/proof`, `@zk-kit/semaphore-artifacts`, and forbade custom circuits.
**Reasoning:**
- *Message slot for the ballot commitment.* Semaphore's circuit does not constrain `message` to anything — it only squares it (`dummySquare <== message * message`) to make the proof non-malleable. Verification then checks `hash(message)` against the public signals, so the value is pinned. That is exactly the property a ballot binding needs: without it, a valid membership proof could be re-attached to a different ciphertext, and the chain would see an authentic proof next to a ballot the voter never cast. Asserted both ways in the suite (valid proof true; re-pointed message false).
- *Scope from the election id.* The circuit computes `nullifier = Poseidon(2)([scope, secret])`, so a constant scope would give every voter one global pseudonym across all elections — keeping double-vote prevention while silently losing unlinkability. Deriving the scope per election gets both properties from one mechanism.
- *Reuse Semaphore's `hash` convention* (keccak256, 32-byte big-endian, `>> 8`) rather than inventing an encoding, so the value is a 248-bit field-safe element and behaves like any other Semaphore scope.
- *No off-circuit nullifier helper.* The nullifier is `Poseidon(2)([hash(scope), secret])`; re-deriving it would need a Poseidon implementation (circomlibjs) and would create a second source of truth for a security-critical value that the proof already reports authoritatively as `proof.nullifier`. Costs a heavier dependency for no benefit.
- *Pin the artifact version* (`SEMAPHORE_ARTIFACTS_VERSION = "4.13.0"`) as a named export. Verified in the installed `@semaphore-protocol/proof@4.14.3` build that this is the version its default resolution pins; a version bump means a different trusted setup, so it must be an explicit recorded change.
**Rejected:**
- *`@zk-kit/semaphore-artifacts` as the artifact source* (the package the instruction named): it ships all 32 depths — 171 MB unpacked as a devDependency — for the 3.7 MB a depth-3 test needs. `@zk-kit/artifacts` is what `@semaphore-protocol/proof` itself uses, resolves the identical files from `snark-artifacts.pse.dev`, and in Node downloads them to the OS temp dir and returns local paths (verified: it does, unmodified). Switching later is a two-line change; recorded in HANDOVER Open items.
- *A custom download/cache helper for tests*: written first, then deleted once `maybeGetSnarkArtifacts` was observed to already download and cache in Node. Dead weight.
- *Poseidon-based scope derivation*: would double-hash as Poseidon→keccak256 inside Semaphore, buying nothing over keccak256 and diverging from how every other Semaphore consumer derives a scope.
- *A typed `BallotCommitment` union from `@keystone/crypto`*: would make circuits depend on crypto and couple the membership subsystem to the encryption subsystem's curve (D-003). The commitment crosses as an opaque scalar instead — now a recorded boundary in ARCHITECTURE.md.
**Tradeoff accepted:** Two hashing conventions live in one feature (keccak256 for scope/message, Poseidon for the nullifier) because that is what the audited circuit does; documented in both modules. The registry-membership pre-check runs only when a `Group` is passed — a `MerkleProof` cannot be validated that way, so that path relies on snarkjs failing.
**Note on a recorded blocker:** HANDOVER listed "unify curves before any `packages/circuits` work" as a gate (from D-003). This work proceeded without unifying them, because ADR-0001 deliberately puts no ElGamal arithmetic inside a circuit — the two subsystems meet only through a hash. The gate as written described a circuit that does not exist in this design. It still applies to any future design that wants ElGamal constraints *inside* a SNARK.
**Revisit if:** Contracts (Phase 3) need the nullifier computed off-circuit for pre-checks — then a Poseidon dependency becomes justified; or the artifact version is bumped; or a design ever places ElGamal inside a circuit (which re-opens D-003).

### D-009 · 2026-09-16 · solar-pro4
**Decision:** Implement `packages/contracts/src/ElectionRegistry.sol` on OpenZeppelin `AccessControl` (role `ELECTION_ADMIN_ROLE`), importing the audited Semaphore verifier interface rather than any Groth16 code. `electionId` is `bytes32`; `dkgPublicKey` is `uint256[2]`; existence is a separate mapping from `merkleRoot`; `updateMerkleRoot` is the only mutation and is gated to strictly before `eligibilityCloseAt`; all four required errors are custom errors. Dependencies are installed with `forge install --no-git --shallow` into a gitignored `lib/` and wired by a committed `remappings.txt`. solc pinned to 0.8.28 with an exact pragma. `forge fmt` adopted as the Solidity formatter.
**Context:** First Solidity in the repo — `packages/contracts` was an empty `forge init` scaffold (only `.gitkeep` files plus a `foundry.toml`). No Foundry toolchain, no `lib/`, no `remappings.txt`, and neither `@openzeppelin/contracts` nor `@semaphore-protocol/contracts` was present anywhere in the repo or the lockfile.
**Reasoning:**
- *`electionId` as `bytes32`.* The registry keys elections by an opaque identifier and never hashes it. The off-chain `electionScope()` already maps any id (string or integer) to a 248-bit scope; storing the scope on-chain instead would bake the off-chain hashing convention into contract storage and lose the ability to look an election up by name. Tradeoff accepted: the contract cannot be queried by scope, so the Phase 3 ballot box must receive the election id alongside the proof's scope and compare `scope == electionScope(id)` itself.
- *`dkgPublicKey` as `uint256[2]`.* `@keystone/crypto` produces an affine point `(x, y)`; a single 256-bit word cannot hold one (a compressed point needs 257 bits). Two words need no agreed compression scheme, cost two slots, and fit any curve narrower than 256 bits — which matters while D-003 (curve choice) is still open. **This is a deviation from the requested single `dkgPublicKey` parameter and should be confirmed.**
- *Existence tracked separately.* The root of an empty Semaphore group is zero, so `merkleRoot == bytes32(0)` is a legitimate value and must not double as "absent". Tested both ways.
- *Verifier pinned, never called.* The registry stores an `ISemaphoreVerifier` address immutably and exposes it; it does not implement or invoke Groth16. This satisfies "import the real verifier, don't rewrite it" while keeping the registry's own duties to configuration. Per-election verifier addresses were rejected as unnecessary complexity for a single audited verifier; signature-only faking was rejected because deploying the real implementation is what proves the import works.
- *Explicit `Unauthorized` instead of `onlyRole`.* The requested error surface names `Unauthorized`, but OZ's `onlyRole` reverts with `AccessControlUnauthorizedAccount`. So the check is an explicit `hasRole` read. AccessControl still owns role storage, granting, and revocation, and role administration still reverts with OZ's own error — which is asserted in the tests so the split is documented by executable behaviour, not prose.
- *Auth before state.* Both gated functions check the role before reading `_registered`, so an unauthorised caller cannot probe which election ids exist.
- *`forge install --no-git` into a gitignored `lib/`.* `.gitignore` already ignores `lib`/`cache`/`out`, so submodule installs (which need committed gitlinks under `lib/`) would fight the ignore rules. `--no-git --shallow` plus a committed `remappings.txt` matches the existing layout. Rejected: npm/pnpm packages with `node_modules` remapping — that needs a `package.json`, which would silently enrol `packages/contracts` in the Turborepo pipeline and the repo-wide `pnpm test`.
- *solc 0.8.28, exact pragma.* The floor is set by dependencies (`>=0.8.23 <0.9.0` Semaphore, `^0.8.20` OZ); 0.8.28 is the smallest common stable choice. An exact pragma plus a pinned compiler makes deployed bytecode reproducible.
**Rejected:** a custom Groth16 verifier or a hand-rolled role bitmask (both explicitly out of scope / reinvent audited code); inferring existence from `merkleRoot`; `onlyRole` with OZ's error; per-election verifier addresses; enforcing `eligibilityCloseAt <= votingCloseAt` at creation (not requested — see HANDOVER Open items).
**Tradeoff accepted:** Dependencies are pinned by *tag in a documented command*, not by anything the repo enforces — a fresh clone must re-run the install before `forge test` works, and a typo'd install could silently pick a different version. `lib/` was gitignored before this change, so this is the repo's own convention rather than a new one; a CI install step is the real fix (Open items).
**Revisit if:** the Phase 3 ballot box needs the scope stored or compared on-chain (then consider storing `electionScope(electionId)` at creation); `@keystone/crypto` settles on an encoding that fits one word; or a verifier upgrade path is needed (the immutable pin means a verifier upgrade requires deploying a new registry).

### D-010 · 2026-09-16 · solar-pro4
**Decision:** Implement `packages/contracts/src/BallotBox.sol` as a permissionless `castVote` that enforces all three properties as a set — Groth16 verification via the registry's pinned verifier, a scope check binding the proof to exactly one election, and a per-election nullifier set — and additionally recomputes the ballot commitment from calldata so a valid proof cannot be re-pointed at a different ciphertext. Ciphertexts travel in the `VoteCast` event, not in storage. `castVote` takes no role.
**Context:** D-009's "Revisit if" anticipated this: the ballot box *does* compare scope on-chain, and doing so forced two cross-language decisions that had no existing answer.
**Reasoning:**
- *Scope derived on-chain through the integer branch.* `ElectionRegistry` stores `bytes32 electionId`, which cannot be turned back into the UTF-8 label `election-scope.ts`'s *string* branch consumes. So the contract recomputes the scope through the *integer* branch: `uint256(keccak256("keystone.election.scope.v1:uint:" ++ bytes32(id))) >> 8`. **Convention established and needing sign-off: election ids are integers, and off-chain callers must derive the scope with `electionScope(BigInt(electionId))`.** The vitest suite for `packages/circuits` uses string ids (`"election-2026-general"`), which produce a different scope and would be rejected by `ScopeMismatch` on-chain. Both branches are legitimate uses of the same module, but the convention must be one of them — and it cannot be both. Flagged in HANDOVER for a decision.
- *Ballot commitment recomputed on-chain.* `castVote` takes the ciphertext and the Chaum-Pedersen proof and hashes them itself, reverting `BallotCommitmentMismatch` if the result is not the proof's `message`. This is what makes proof-swapping fail: without it, a valid proof could be submitted beside someone else's ciphertext. The formula is deliberately `abi.encodePacked`-simple — plain concatenation of the proof bytes and four 32-byte words, trimmed to 248 bits — so TypeScript reproduces it byte for byte with no ABI-encoding offsets.
- *That agreement is pinned by a test, not by prose.* `packages/circuits/scripts/generate-contract-fixtures.mjs` generates real proofs on the audited circuit and writes `packages/contracts/test/fixtures/vote-proofs.json`, computing the commitment with the TypeScript formula. The Foundry suite loads those proofs and asserts the contract accepts them — so if either side's formula drifts, `test_CastVote_AcceptsRealCircuitProof` fails. This is also the first test that runs a proof from this repository through the real Semaphore verifier; nothing about the on-chain path was assumed.
- *`message`/`scope` reach the verifier hashed.* Verified empirically against the generated fixture (the proof object carries the **raw** values), then implemented verbatim as Semaphore's `_hash`. Getting this wrong fails every proof while looking correct.
- *Ballots in events, not state.* The tally is threshold decryption performed off-chain, so the ciphertext is needed by the indexer, not by the EVM. Storing four words per ballot buys nothing the event does not record. State is limited to nullifiers, which is the only thing that must be checked on-chain later.
- *Permissionless.* A valid proof *is* the authorisation; the only thing a malicious submitter could abuse is a spent nullifier, which is rejected. A role gate would add nothing but would block the voter client.
- *Chaum-Pedersen proof is not verified on-chain.* secp256k1 arithmetic is not affordable in the EVM and would couple the ballot box to D-003. Its correctness is established off-chain; the contract binds it (by hashing it into the commitment) without evaluating it. Documented in the contract header as a deliberate trust boundary.
- *Registry errors are reused, not duplicated.* An unknown election reverts with `ElectionRegistry.ElectionNotFound` — one error, clear provenance. Only errors BallotBox can raise on its own are defined here.
- *Depth bounds come from Semaphore's own `Constants`* (`MIN_DEPTH`/`MAX_DEPTH`), not a local literal, because the verifier indexes its verification key by depth and an out-of-range depth is undefined behaviour rather than a clean revert.
**Rejected:** storing the scope in `ElectionRegistry` at creation (cleaner mapping, but it reopens a frozen ABI — D-009 — and the integer-branch convention avoids it); storing ciphertexts in state; a role-gated `castVote`; verifying Chaum-Pedersen on-chain.
**Tradeoff accepted:** the commitment formula lives in two languages and is kept in step only by the fixture test. The scope convention lives in two places (TS module and Solidity constant) and is kept in step the same way. Both are versioned domain separators, so a bump is a deliberate act — but the two-source-of-truth risk is real and is the reason `test_ElectionScope_MatchesOffChainDerivation` exists.
**Revisit if:** the indexer needs ciphertexts from state rather than events; the scope convention is changed to strings (which requires storing or passing the label on-chain); or D-003 lands a curve that makes on-chain validity proofs affordable.
